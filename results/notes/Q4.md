## 1. Executive Summary

This report delivers a rigorous empirical serving and scale analysis for the two-stage retrieve-then-rank news recommendation pipeline. In Stage 1, dense semantic candidate retrieval is accelerated using **FAISS HNSW** (`IndexHNSWFlat`, $M = 32$, $\text{efSearch} = 64$) coupled with lexical Okapi BM25 scoring. In Stage 2, a 10-feature point-in-time LightGBM LambdaMART model scores and re-ranks the top-$K = 100$ candidates.

### Key Benchmark Takeaways:
1. **Strict SLA Compliance ($\text{p99} < 100\text{ ms}$):**
   - **MIND:** Impression scoring $\text{p99} = 37.89\text{ ms}$ (mean $9.93\text{ ms}$); full-catalog retrieval $\text{p99} = 36.75\text{ ms}$.
   - **EB-NeRD:** Impression scoring $\text{p99} = 26.99\text{ ms}$ (mean $9.91\text{ ms}$); full-catalog retrieval $\text{p99} = 32.64\text{ ms}$.
   - Both pipelines pass the production serving deadline with **$> 2.6\times$ to $3.7\times$ safety margin**.
2. **Memory Footprint & Graph Overhead:**
   - **MIND (Small, $N = 65{,}238$, $384\text{-dim}$):** Exact Flat index consumes $95.56\text{ MB}$; HNSW index consumes $112.50\text{ MB}$ (graph overhead: $+16.93\text{ MB}$, $+17.7\%$). Total serving RAM: $204.50\text{ MB}$.
   - **EB-NeRD (Demo, $N = 11{,}777$, $768\text{-dim}$):** Exact Flat index consumes $34.50\text{ MB}$; HNSW index consumes $37.56\text{ MB}$ (graph overhead: $+3.06\text{ MB}$, $+8.9\%$). Total serving RAM: $74.82\text{ MB}$.
   - Large catalog scaling ($N \sim 125\text{K}\text{--}130\text{K}$) expands index memory proportionally to $224.83\text{ MB}$ (MIND) and $400.39\text{ MB}$ (EB-NeRD), adhering strictly to $O(N \cdot D + N \cdot M)$ complexity.
3. **Accuracy Preservation Under Approximate Retrieval:**
   - Stage 2 Re-Ranker on EB-NeRD achieves **$\text{AUC} = 0.7045$** ($+41.2\%$ over Stage 1 prior of $0.4991$) and **$\text{nDCG@5} = 0.5291$** ($+54.2\%$ over Stage 1 prior of $0.3431$).
   - Stage 2 Re-Ranker on MIND achieves **$\text{AUC} = 0.5754$** ($+7.5\%$ over Stage 1 prior of $0.5350$) and **$\text{nDCG@5} = 0.2697$** ($+14.0\%$ over Stage 1 prior of $0.2365$).
   - Ranking quality is virtually identical to exact Flat search ($\Delta \text{AUC} < 0.0005$), confirming that HNSW graph approximations do not degrade end-to-end recommendation fidelity.
4. **Economic Serving Viability:**
   - On an 8-vCPU cloud instance (e.g., AWS `c6i.2xlarge` @ \$0.34/hr), serving throughput reaches **$\sim 564\text{ QPS}$**, translating to **\$0.000167 per $1{,}000$ queries** (\$0.167 per million queries) or **$\sim 5.98$ million queries per dollar**.

## 2. Pipeline Serving Architecture

```
User Impression Request (user_id, timestamp, candidate_pool)
   │
   ├──► [Temporal Boundary Enforcer] (Anti-Gaming, Q9 Compliance)
   │       Drops any click where t_click >= t_imp (strictly zero future leakage)
   │
   ├──► [Stage 1: Candidate Generation / Prior Retrieval] (Top-K = 100)
   │       ├─ Dense Semantic Search: FAISS IndexHNSWFlat (M=32, efSearch=64)
   │       ├─ Lexical Matching: BM25 Inverted Index
   │       └─ Fusion Prior: Reciprocal Rank Fusion (RRF) / max(BM25, Semantic)
   │
   └──► [Stage 2: LightGBM LambdaMART Re-Ranker]
           ├─ 9 Point-in-Time Features:
           │    1. user_click_count
           │    2. user_recency_score (exponential decay w = 0.5^(dt / 24h))
           │    3. user_mean_dwell_time (seconds)
           │    4. article_freshness_hours ((t_imp - t_pub) in hours)
           │    5. category_affinity_score (historical fraction in category)
           │    6. session_position (presentation rank bias)
           │    7. bm25_score (lexical token score)
           │    8. semantic_score (dense user-article cosine similarity)
           │    9. first_stage_score (Stage 1 retrieval prior)
           └─ Output: Re-ranked candidate ranking sorted descending by score
```

### Mathematical Memory Formulation

The memory consumed by `faiss.IndexHNSWFlat` decomposes analytically into:
$$\text{Memory}_{\text{HNSW}} = \text{Memory}_{\text{vectors}} + \text{Memory}_{\text{graph}}$$

1. **Vector Storage:**
   $$\text{Memory}_{\text{vectors}} = N \cdot D \cdot 4\text{ bytes}$$
   Each vector requires $D \times 4\text{ bytes}$. For EB-NeRD ($D = 768$), each vector takes $3{,}072\text{ bytes}$; for MIND ($D = 384$), each vector takes $1{,}536\text{ bytes}$.
2. **Graph Structure Overhead:**
   In HNSW, each node stores proximity links across hierarchical graph layers. With base link degree $2M = 64$ and upper link degree $M = 32$:
   $$\text{Memory}_{\text{graph}} \approx N \cdot (2M) \cdot 4\text{ bytes} + N \cdot \text{metadata} \approx 256\text{ to }270\text{ bytes per node}$$
   Because graph overhead is invariant to dimension $D$, its relative overhead is smaller on higher-dimensional embeddings ($8.9\%$ on EB-NeRD vs. $17.7\%$ on MIND).

## 7. Sub-Question 3: Cost / QPS Back-of-Envelope Projections

To model cloud deployment economics, we benchmark against a standard cloud compute node:
- **Reference Instance:** AWS EC2 `c6i.2xlarge` (8 vCPUs, 16 GB RAM, Intel Xeon Ice Lake).
- **On-Demand Hourly Rate:** \$0.34 per hour.
- **Serving Concurrency Efficiency:** $70\%$ parallel scaling efficiency factor across 8 physical vCPUs.

### Economic Model Calculations

1. **Single-Core Throughput:**
   $$\text{QPS}_{\text{core}} = \frac{1{,}000\text{ ms}}{\text{Mean Latency (ms)}} \approx \frac{1{,}000}{9.92} \approx 100.8\text{ queries/sec/core}$$
2. **Instance Capacity (8 vCPUs):**
   $$\text{QPS}_{\text{instance}} = \text{QPS}_{\text{core}} \times 8 \times 0.70 \approx 564\text{ QPS}$$
3. **Hourly Query Volume:**
   $$\text{Queries/Hour} = 564.5 \times 3{,}600 \approx 2{,}032{,}200\text{ queries/hour}$$
4. **Cost Per Unit Query:**
   $$\text{Cost per 1,000 Queries} = \frac{\$0.34}{2{,}032{,}200} \times 1{,}000 \approx \mathbf{\$0.000167}$$
   $$\text{Cost per 1,000,000 Queries} = \mathbf{\$0.167}$$
   $$\text{Queries per Dollar} = \frac{1}{\$0.000167 / 1{,}000} \approx \mathbf{5{,}980{,}000\text{ queries/\$}}$$

## 8. Sub-Question 4: 10× Scaling Argument — What Breaks First?

If our system scales to **$10\times$ current load** ($\sim 1.2\text{M}$ articles, $27\text{M}$ users, $6{,}000\text{ concurrent QPS}$, and $600\text{M}$ clicks), the existing single-node architecture encounters specific structural bottlenecks. Below is the technical breakdown of what breaks first, why, and the architectural remedy:

### Bottleneck 1: On-the-Fly Feature Extraction & Python Dict Serialization (Breaks First!)
- **Why it breaks:** In the current implementation, every incoming request extracts point-in-time behavioral features by filtering click timestamps, computing exponential recency weights, and aggregating category affinity in Python. At $6{,}000\text{ QPS}$, Python GIL and per-request loop overhead will saturate CPU cores, causing $\text{p99}$ latency to explode beyond $250\text{ ms}$.
- **Architectural Remedy:**
  - Decouple feature extraction from online request serving using a real-time streaming feature store (e.g., **Feast** or **Redis Cluster**).
  - Pre-materialize decay-weighted user preference vectors asynchronously upon click ingestion via Kafka/Flink.
  - Serving-time feature lookup drops from an $O(H)$ history scan to an $O(1)$ memory key-value lookup ($< 0.5\text{ ms}$).

### Bottleneck 2: In-Memory BM25 Inverted Index
- **Why it breaks:** At $10\times$ catalog scale ($1.2\text{M}$ articles), the in-memory inverted index posting lists grow to several gigabytes. Token intersection across long posting lists causes CPU cache thrashing and memory bus contention.
- **Architectural Remedy:**
  - Implement **WAND (Weak AND)** or **Block-Max WAND (BMW)** dynamic posting-list pruning to skip evaluation of documents that cannot enter the top-$K$.
  - Shard the inverted index horizontally across an Elasticsearch/OpenSearch cluster with replica query routing.

### Bottleneck 3: FAISS HNSW Index RAM Saturation
- **Why it breaks:** At $1.2\text{M}$ articles with $768\text{-dim}$ float32 embeddings, raw vectors require $3.68\text{ GB}$ and HNSW graph edges require $\approx 400\text{ MB}$. While $4\text{ GB}$ fits in RAM, building or rebuilding HNSW dynamically for $1.2\text{M}$ articles takes several minutes, blocking real-time index freshness.
- **Architectural Remedy:**
  - Transition from `IndexHNSWFlat` to **Inverted File with Product Quantization (`IndexIVFPQ`)** or **ScaNN (Anisotropic Vector Quantization)**.
  - Quantizing $768\text{-dim}$ vectors into 64 bytes achieves an **$8\times$ memory reduction** ($3.68\text{ GB} \to 460\text{ MB}$), keeping the entire catalog resident in high-speed CPU L3 cache.

### Bottleneck 4: Re-Ranker Tree Scoring Throughput
- **Why it breaks:** Scoring 100 candidate items with 100 LightGBM decision trees using pure Python bindings incurs overhead in array conversions and C-API boundary crossing.
- **Architectural Remedy:**
  - Compile the LightGBM decision ensemble into optimized C++ machine code using **Treelite** or deploy on **Triton Inference Server** with **ONNX Runtime**.
  - Compiled tree scoring achieves vectorization via AVX-512 SIMD instructions, reducing Stage 2 re-ranking latency from $5\text{ ms}$ to $< 0.4\text{ ms}$.
